|---|---|---|---|---|
| Техническая | OAuth2/OIDC: JWT от IdP, проверка подписи, iss/aud/exp; user_id = claim sub; заголовок X-User-Id отклоняется на шлюзе | Spoofing — первопричину IDOR (RC-1) | код + инфраструктура (шлюз) | запрос без токена или с X-User-Id вместо токена → 401 |

## Описания и меры по всем карточкам

### #1. TOP-1. IDOR/BOLA: перевод с чужого счёта и чтение чужой истории через подмену X-User-Id

*Элемент:* Bank Microservice API (FastAPI + uvicorn :8000) · *STRIDE:* Elevation of privilege · *Критичность:* Critical · *Статус:* Open · *Оценка:* 9.1 (Critical)

**Описание.** [RC-1] Причина: идентичность берётся из клиентского заголовка X-User-Id без проверки (app/security.py:3-13); проверка владения (app/crud.py:5-13) сравнивает счёт с этим же значением.
Предпосылки: сетевой доступ к API, без учётной записи; ID последовательные.
Объекты: для перевода — счёт списания и его владелец; для истории — исходящие операции счетов выбранного владельца (JOIN по счёту отправителя, не более limit ≤ 100 за запрос; app/crud.py:52-65).
Подтверждено: X-User-Id: 1 → перевод со счёта 1 и одна исходящая операция пользователя 1 (dynamic_checks.log:13-14, 17-18).
Импакт: C — High (исходящие операции любого владельца при подстановке его X-User-Id), I — High (списание с любого счёта), A — нет. CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N.
Бизнес: хищение средств, раскрытие банковской тайны. Связано: #4 (та же причина).

**Меры.** Рекомендации: Т, код + шлюз: OIDC/JWT, user_id = sub, X-User-Id отклоняется.
Т, код: владение в том же SQL, 404 для чужих объектов.
А: API-шлюз, второй фактор для перевода, UUID счетов.
П: тесты A→B как gate в CI, DAST.
Критерий: чужой субъект → 404, 0 изменений в БД.
Полная таблица мер — threat-register.md.

### #2. TOP-2. Race condition (TOCTOU) в переводе: списание сверх остатка, отрицательный баланс

*Элемент:* Bank Microservice API (FastAPI + uvicorn :8000) · *STRIDE:* Tampering · *Критичность:* Critical · *Статус:* Open · *Оценка:* 7.5 (High); бизнес: Critical

**Описание.** [RC-2] Причина: баланс читается без блокировки (app/crud.py:22), проверка bal < amount — в приложении, затем отдельный UPDATE (app/crud.py:32); в схеме нет CHECK (balance_cents >= 0).
Предпосылки: параллельные запросы со своего счёта — угроза остаётся после исправления TOP-1.
Подтверждено: отрицательный остаток отправителя — race_check.log: 4 из 10 раундов (до −30000); дополнительный прогон race_invariant_check.log: 8 из 10. Получатель зачисляется по каждой успешной операции — необеспеченные зачисления на сумму отрицательного остатка. Сумма остатков по всем счетам в раунде не менялась: нарушен инвариант неотрицательного баланса, а не сохранения суммы. Вывод необеспеченных средств не проверялся.
Импакт: I — High, C/A — нет. CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N (PR:L после TOP-1 → 6.5).
Бизнес: риск финансовых потерь, расхождение остатков. Связано: #17.

**Меры.** Рекомендации: Т, код: условный UPDATE … WHERE balance >= amount RETURNING или SELECT … FOR UPDATE.
Т, схема БД: CHECK (balance_cents >= 0), FK.
А: Idempotency-Key + UNIQUE, журнал проводок и сверка.
П: конкурентный тест в CI, алерт на минус.
Критерий: race_check 10×30 — 0 отрицательных остатков.
Полная таблица мер — threat-register.md.

### #3. TOP-3. Доступ к PostgreSQL и Redis в обход API: опубликованные порты, пароль по умолчанию, Redis без пароля

*Элемент:* PostgreSQL 16 (БД bank: accounts, transactions) · *STRIDE:* Tampering · *Критичность:* Critical · *Статус:* Open · *Оценка:* 9.8 (Critical) при доступе из внешней сети

**Описание.** [RC-3] Причина (microservice/docker-compose.yml): порты 5432 и 6379 опубликованы на всех интерфейсах (стр. 10-11, 17-18), учётка postgres/postgres (стр. 7-8, 23), Redis без пароля (стр. 24).
Предпосылки: сетевой доступ к хосту.
Подтверждено: конфигурацией и Semgrep (bank.compose-*); влияние записи в Redis на ответ API — шаг 7. Подключение к опубликованным портам не выполнялось: стенд работал без Docker.
Импакт: C/I/A — High: чтение и изменение балансов и истории, сброс кэша в обход проверок и журналов API. CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H (AV:A = 8.8 для внутреннего сегмента).
Бизнес: компрометация ядра переводов, простой. Связано: #15, #20, #21, #22.

**Меры.** Рекомендации: А, инфраструктура: убрать ports у postgres/redis, внутренняя сеть, bastion.
Т, конфигурация: секреты из secret store, роль с минимальными правами, Redis ACL.
Т: TLS к PostgreSQL и Redis.
П: gate bank.compose-*, сканирование периметра.
Критерий: 5432/6379 извне — closed/filtered.
Полная таблица мер — threat-register.md.

### #5. Потенциальная регрессия к SQL Injection при изменении сборки SQL (search, limit)

*Элемент:* Bank Microservice API (FastAPI + uvicorn :8000) · *STRIDE:* Tampering · *Критичность:* Medium · *Статус:* Open · *Оценка:* н/п: уязвимость не обнаружена

**Описание.** [RC-5] Наблюдение: запрос собирается f-строками (app/crud.py:61, 64); Semgrep: bank.dynamic-sql-fstring, asyncpg-sqli (app/crud.py:66).
Действующая защита (в коде): в f-строку попадают только номера плейсхолдеров $2/$3, значения search и limit передаются bind-параметрами asyncpg.
Задание указывает на SQL Injection; для поставки с SHA-256 b34bebec…6458b3 значения пользователя передаются параметрами conn.fetch(sql, *params) (app/crud.py:66) — SQL Injection в этом запросе не подтверждена; триаж Semgrep — false positive по эксплуатируемости. Лог (иллюстрация): ' OR '1'='1 → [] (dynamic_checks.log:25-26).
Риск: правка вида f"... '{search}'" сделает инъекцию возможной, а работа под суперпользователем (#9) — максимальной по импакту. Связано: #9.

**Меры.** Действует: bind-параметризация asyncpg.
